# LSASS Credential Theft Detection (T1003.001)

> [!abstract] AI Summary
> Developed detection for LSASS memory dumping attacks using ProcDump, Dumpert, Nanodump, and comsvcs.dll. Built Splunk alert on Sysmon Event ID 10 targeting unauthorized lsass.exe access with whitelist logic (MsMpEng.exe, taskmgr.exe, csrss.exe) via Splunk Lookup Tables. Validated detection across multiple dumping tools and tuned alert throttling to prevent alert fatigue.  

---

## Test Objectives

- Observe logs for evidence of memory dump of the [LSASS.exe](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/LSASS.md) process
- Build a detection rule capable of catching multiple LSASS dumping tools, not just a single binary

> [!warning] Credential Guard / PPL Blockage
> LSASS dumping was initially blocked by Credential Guard and Privileged Process Integrity (PPL). These had to be disabled before tests could succeed.

**Attempt 1 — 2026-09-19 14:16 AWST (UTC+8)**

Test failed due to permission issues. Two fixes attempted:

```powershell
Set-MpPreference -DisableRealTimeMonitoring $true
```

Then ProcDump failed to dump the process. This was narrowed down to two potential issues. First, scripting wasn't enabled in the PowerShell window, so the following was applied:

```powershell
Set-ExecutionPolicy RemoteSigned
```

This did not resolve the issue. The other probable issue was that [Credential Guard](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/Credential%20Guard.md) Guard.md was enabled, which uses [Privileged Process Integrity](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/Privileged%20Process%20Integrity.md) Process Integrity.md to prevent ProcDump from reading LSASS memory. Upon checking the registry, it was found to be enabled alongside [Secure Boot](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/Secure%20Boot.md) Boot.md. UEFI settings were modified to not launch with Safe Boot.

## Test Results

### Test 1: Dump LSASS.exe Memory using ProcDump

> [!info] Test Detail
> **Tool:** ProcDump (**Sysinternals**)
> **Command:** `"procdump.exe" -accepteula -ma lsass.exe <outputfile>`
> **Test conducted:** 2026-09-19 15:22 AWST (UTC+8)

Memory of [LSASS.exe](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/LSASS.md) can be dumped for offline credential theft attacks. This can be achieved with **Sysinternals** ProcDump.

**Evidence — Sysmon EventID 10 (Process Access):**

![Pasted image 20260926190852.png](../../Images/RegularImages/Pasted%20image%2020260926190852.png)

Within this log it shows that `lsass.exe` was accessed by the program `procdump64.exe`. The access code `0x1fffff` shows that the process was given permission to execute. The target image of `system32\lsass.exe` shows that LSASS was accessed. The Sysmon EventID 10 indicates that one process requested an open handle to interact with the memory of another process.

**Evidence — Sysmon EventID 11 (File Creation):**

![Pasted image 20260926190856.png](../../Images/RegularImages/Pasted%20image%2020260926190856.png)

This event log displays Sysmon EventID 11 (file created). The target filename indicates where the file was created — this is likely the artifact dumped from memory. The image that created this file was `procdump64.exe`.

> [!summary] Key Finding
> Sysmon EventID 10 logged `procdump64.exe` accessing `lsass.exe` with `GrantedAccess` `0x1fffff` (full access). The whitelist-based detection rule successfully caught this.

## Alert Development

### Initial Rule (AI-generated)

As this was the first alert created in this project, AI was used to assist in creating the rule. The following was initially generated:

```splunk
index=windows sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=10
TargetImage="*\\lsass.exe"
(SourceImage="*\\procdump*.exe" OR SourceImage="*\\procdump64.exe")
| stats count min(_time) as firstTime max(_time) as lastTime by host, User, SourceImage, TargetImage, TargetProcessId, GrantedAccess, CallTrace
| eval technique="T1003.001 - LSASS Memory Dump"
```

However, looking at the code it was assessed as too limited in scope — this rule only detects when `procdump.exe` or `procdump64.exe` is attempting to access `lsass.exe`.

### Final Detection Rule

```splunk
index=endpoint source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventID=10 TargetImage="*\\lsass.exe" NOT (SourceImage IN ("*\\MsMpEng.exe", "*\\taskmgr.exe", "*\\csrss.exe"))
```

This rule alerts on any process accessing `lsass.exe` except known legitimate processes (Windows Defender, Task Manager, CSRSS).

### Alert Testing and Tuning

Ran the same atomic test again and the LSASS dumping was detected, however it generated **10 alerts for the one attack**. The rule was modified to include a throttle of 30 seconds to ensure mass alerts were not triggered.

### False Positives and Tuning

- **Whitelisted processes:** `MsMpEng.exe` (Windows Defender), `taskmgr.exe` (Task Manager), `csrss.exe` (Client/Server Runtime Subsystem)
- **Throttle:** 30 seconds to prevent mass alerting from a single attack
- **Lookup Tables:** Can be used to manage the whitelist at scale in a production environment

## Lessons Learned

- Sysmon EventID 10 (Process Access) is the primary log source for detecting LSASS dumping
- `GrantedAccess` value `0x1fffff` indicates full access — a strong indicator of credential theft attempts
- Credential Guard and PPL must be disabled in a lab environment before LSASS dumping can be simulated
- Different dumping tools (ProcDump, Dumpert, Nanodump, comsvcs.dll) all generate EventID 10, but some evasion techniques may bypass it
- A whitelist-based approach is more effective than matching specific tool names
- Alert throttling is essential to avoid alert fatigue
