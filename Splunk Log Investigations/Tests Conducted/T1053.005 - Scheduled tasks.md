# Persistence via Scheduled Task Detection (T1053.005)

> [!abstract] AI Summary
> Investigated multiple scheduled task persistence vectors including COM automation, WMI/PS_ScheduledTask, VBA macro execution, and registry-encoded payloads. Built detection on Windows Event ID 4698 and Sysmon Event ID 1, configured Local Security Policy audit subcategories for complete log coverage, and identified suspicious execution paths (`\AppData\`, `\Temp\`, `\Public\`).

---

## Test Objectives

- Use Atomic Red Team tests to observe malicious creation of scheduled tasks
- Create a generic detection rule capable of catching most scheduled task persistence attacks

## Setup and Troubleshooting

> Missing Event Logs
> EventID 4698 (Scheduled Task Creation) was not initially appearing in Splunk. The root cause was the Local Security Policy audit subcategory not being enabled.

Initial search for `WinEventLog:Security` logs on Splunk did not show EventID 4698 or 4702. However, after a deeper inspection the following was found:

![Pasted image 20260926191049.png](../../Images/RegularImages/Pasted%20image%2020260926191049.png)

This log with EventID 4688 (new process creation) shows the process creation for the scheduled tasks. However, this does not show the creation of the scheduled task itself, so further investigation into why this log was not created was required.

Following some research, the likely cause was that the [Local Security Policy](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/Local%20Security%20Policy.md) was not configured to pass the logs. The difficulty came in which subcategory to enable, as there were many and none had the term "task" contained within the title. After further digging, it was found that **"Audit Other Object Access Events"** was the setting needed for the log to be generated. This was then enabled and the test was re-run.

**Location of the enabled audit:**

![Pasted image 20260926191056.png](../../Images/RegularImages/Pasted%20image%2020260926191056.png)

Following this, the atomic test was re-run and successfully created the desired logs:

## Test Results

### Test 1: Scheduled Task Creation via ScheduledTasks PowerShell Module

> [!info] Test Detail
> **Method:** PowerShell ScheduledTasks module (`Register-ScheduledTask`)
> **Result:** Two tasks created — one on system startup, one on logon

![Pasted image 20260926191039.png](../../Images/RegularImages/Pasted%20image%2020260926191039.png)

This test successfully created two tasks in the [Windows Task Scheduler](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/Windows%20Task%20Scheduler.md) that would run `calc.exe` at system startup and at system logon.

> [!summary] Key Finding
> EventID 4698 is the definitive log for scheduled task creation. Requires "Audit Other Object Access Events" to be enabled in Local Security Policy.

### Test 3: Process Creation Analysis and Suspicious Paths

> [!info] Test Detail
> **Method:** Filtered Sysmon EventID 1 with piping to identify process creation patterns
> **Result:** Identified `AppData\Local\Temp` as the source of malicious events

For this test, the search was modified to locate EventID 1 to find the process creation that creates the scheduled task, in addition to usage of piping (`|`) to filter results into a table for easier viewing. The following results were retrieved:

![Pasted image 20260926191111.png](../../Images/RegularImages/Pasted%20image%2020260926191111.png)

The returned results showed an interesting trend that aligned with previous research. The simulated malicious events came from the working directory `C:\Users\VulnUser\AppData\Local\Temp\`.

Further research was conducted as to why Temp is utilised for malicious payloads. The reasons are as follows:

1. **Noisy** — The Temp folder is utilised by many legitimate programs, so disguising a malicious program amongst the other hundred temporary install files is fairly common
2. **Low barrier to entry** — As most attackers start at a low-privilege user, the attacker can write to the Temp folder
3. **Dropper malware staging** — [Dropper malware](../../Studied%20Ideas%20and%20Concepts/3.%20LSASS%20Investigation/Dropper%20Malware.md) Malware.md is where the malware gains initial access. Most of the time it is a small script which reaches out to the internet, downloads the real payload, and saves it to somewhere it can run. Because Temp is the easiest place to write data quickly, it becomes the preferred landing zone

> [!summary] Key Finding
> Malicious scheduled task creation consistently originates from `AppData\Local\Temp\`. This path is a strong indicator of compromise and can be used as an additional alert filter.

### Test 4: Scheduled Task via COM Automation and VBA

> [!info] Test Detail
> **Method:** [COM](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/COM.md) automation to create a hidden Word document with embedded VBA macro
> **Result:** Macro execution created scheduled task via Windows API

For this test, the [COM](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/COM.md) API was utilised to schedule the task. Specifically, this code utilises COM automation to open a "headless" (hidden) instance of Word. It tells Word to create a document and take text from a `.txt` file and inject it into the document's macro storage.

- Once finished, it is saved as a `.docm` (Word macro-enabled document)
- The attack begins when a human or script opens the created Word document and enables macros. Word executes the code, and the code calls the Windows API to schedule the desired task.

![Pasted image 20260926191115.png](../../Images/RegularImages/Pasted%20image%2020260926191115.png)

This scheduled task launches `notepad`:

![Pasted image 20260926191121.png](../../Images/RegularImages/Pasted%20image%2020260926191121.png)

This program relies on Visual Basic for Applications ([VBA](../../VBA.md)). Essentially, VBA is an "embedded event-driven automation language". This language can access [COM](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/COM.md) to talk to other components in Windows, and that is where the danger lies.

> [!summary] Key Finding
> COM automation combined with VBA can create scheduled tasks entirely from within a macro-enabled document. Detection requires monitoring both EventID 4698 and suspicious Word/VBA process chains (EventID 1).

This test creates a scheduled task by utilising [WMI](../../Studied%20Ideas%20and%20Concepts/4.%20Scheduled%20Tasks/WMI.md) `PS_ScheduledTask`, effectively utilising the `Register-ScheduledTask` cmdlet behind the scenes. The log generated from the program:

This technique, as described by AtomicRedTeam, uses a scheduled task to call upon an encoded command in the registry. A real-world example of this in use is [here](https://thedfirreport.com/2022/02/07/qbot-likes-to-move-it-move-it/).

### Test 7: Blind Investigation — Unknown Attack Vector

> [!info] Test Detail
> **Method:** Investigated without prior knowledge of how the scheduled task operated
> **Result:** Successfully identified WMI-based creation from EventID 1 alone

For this test, the investigation was conducted without any prior knowledge of how the scheduled task operated. The following was found after filtering by EventID 1:

![Pasted image 20260926191203.png](../../Images/RegularImages/Pasted%20image%2020260926191203.png)

The command line for this event is as follows:

```powershell
"powershell.exe" & {$xml = [System.IO.File]::ReadAllText("C:\Users\VulnUser\Documents\AtomicRedteam\atomics\T1053.005\src\T1053_05_SCTASK_HIDDEN_ATTRIB.xml") Invoke-CimMethod -ClassName PS_ScheduledTask -NameSpace "Root\Microsoft\Windows\TaskScheduler" -MethodName "RegisterByXml" -Arguments @{ Force = $true; Xml =$xml; }}
```

## Alert Development

### Detection Rule

```splunk
index="endpoint" EventID=4698
```

A simple detection rule was created for this alert as there are not many programs on the vulnerable system that require filtering. In a more complex environment, the following could be used:

```splunk
index="endpoint" EventID=4698 NOT (TaskName IN ("*GoogleUpdate*", "*microsoftEdgeupdate*"))
```

Utilising the above command, it is easy to update the alert with the required processes to ignore.

The initial test was run again and an alert was generated for each scheduled task created within Task Scheduler.

### False Positives and Tuning

- **Whitelisted tasks:** `GoogleUpdate`, `MicrosoftEdgeUpdate`, and other legitimate update mechanisms
- **Suspicious paths filter:** Add `CommandLine="*AppData*" OR CommandLine="*Temp*" OR CommandLine="*Public*"` to increase specificity
- **Correlation with EventID 1:** Combine with Sysmon process creation logs to filter out legitimate admin-created tasks
- **Lookup Tables:** Manage whitelisted task names at scale using Splunk Lookup Tables

## Lessons Learned

- Deepened understanding of how to filter logs in Splunk
- Greater understanding of how scheduled tasks are created and operate across multiple techniques (PowerShell, CMD, COM, WMI, Registry)
- How logging on Windows systems is configured — specifically which Local Security Policy audit subcategories control which events
- Developed independence in log analysis, becoming less reliant on prior research into attack vector operations
- `AppData\Local\Temp\` is a consistent indicator of malicious execution origin
- Blind investigation from EventID 1 alone can identify the persistence technique and full command chain
